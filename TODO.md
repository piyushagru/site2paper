# Roadmap

Priorities:

- **P0**: breaks a promise the README makes, blocks public use, or is a licence or attribution requirement.
- **P1**: a clear need with a cited source, a gap found in the code, or an item the owner asked for.
- **P2**: competitor parity or a nice-to-have.

Tiers: **T1** under 50 changed lines, **T2** 50 to 200 lines, **T3** needs an owner decision before code (new format, new config surface, new dependency, release or publish step).

Vision: one command that turns any website into the print, text and screenshot outputs people need, with the same zero-config start.

## P1

Code items first. A cycle without a code commit is not finished (owner, 2026-11-09).

- **P1-20 `--pages <file>` that cannot be read fails after Chrome is open.** `run()` in `src/cli.mjs` calls `readFileSync(o.pages)` after `launchBrowser()`, so a typo in the path costs a Chrome launch and ends in the raw Node line `ENOENT: no such file or directory, open '...'`. Smallest fix: read the file before the launch and rethrow as `cannot read --pages file <path>: <reason>`. Tier T1. Source: [clig.dev, Errors](https://clig.dev/#errors) ("catch errors and rewrite them for humans"), deep dive 2026-11-11.
- **P1-22 Sitemaps named in `robots.txt` are never read.** `fromSitemap()` in `src/discover.mjs` fetches only `<origin>/sitemap.xml`. A site whose sitemap lives at `/sitemap_index.xml` or `/sitemaps/pages.xml` (WordPress, Shopify and most generators, announced on `Sitemap:` lines in `/robots.txt`) falls back to the browser crawl: minutes slower, and pages not linked from any page are missed. Smallest fix: fetch `/robots.txt` first, take every `Sitemap:` line on the same origin, then try `/sitemap.xml` only when there is none; `parseSitemap` and the index handling stay as they are. Tier T1. Source: [Google, large sitemaps](https://developers.google.com/search/docs/crawling-indexing/sitemaps/large-sitemaps.md.txt) (referenced sitemaps must be on the same site), [sitemap discovery via robots.txt](https://dev.to/datawrightlabs/extract-every-url-from-a-sitemapxml-in-python-indexes-gz-robotstxt-and-spot-competitors-new-gk4), deep dive 2026-11-12.
- **P1-28 A sitemap index with more than 10 children loses pages silently.** `fromSitemap()` in `src/discover.mjs` reads `locs.slice(0, 10)` of an index, all at once, and only then applies `limit`. A site whose index lists 12 child sitemaps (posts split by month, one per language) never prints the pages in children 11 and 12, and no crawl runs because the sitemap did return pages; 10 children at the protocol maximum of 50 000 URLs each are held in memory before the cut. Smallest fix: walk the children in index order, one fetch at a time, and stop as soon as the deduplicated same-origin list reaches `limit`. Tier T1. Source: [Google, large sitemaps](https://developers.google.com/search/docs/crawling-indexing/sitemaps/large-sitemaps.md.txt) (50 000 URLs per file, an index lists many files), deep dive 2026-11-13.
- **P1-29 A start URL that redirects to another host finds one page.** `example.com` redirecting to `www.example.com`, or `http://` to `https://`, is one host for the user and two origins for `sameOrigin()`. `fromSitemap()` drops every `<loc>` on the final host, so the run falls back to the crawl; `crawl()` opens the start URL, every link on the page is on the final host, all are dropped, and the run says `Found 1 page(s) by crawling`. Smallest fix: in `run()` (`src/cli.mjs`), resolve the start URL once with `fetch(start, { redirect: "follow" })` and use `res.url` as `start` before discovery, with a line `redirected to <origin>` when it changed; one test with a stubbed `fetch`. Tier T2 (the origin the user typed changes; the owner may want to call it T3). Source: [Google, robots.txt spec](https://developers.google.com/crawling/docs/robots-txt/robots-txt-spec) (a host, protocol and port is its own site: `www.` and the apex are distinct), deep dive 2026-11-13.
- **P1-18 Discovery budget.** Without a sitemap, discovery loads up to 50 pages in a full browser before capture starts, then capture loads them all again; on a large site discovery alone takes minutes. Options: stop crawling after a time budget and say how many pages were found and how to widen it (`--limit`, `--pages`), or capture while crawling. Tier T2, open.
- **P1-19 Bot-check pages.** Large retail sites may answer a headless browser with a challenge page. `ERROR_TEXT` does not match those, so the page would print as the challenge. Detect and report "blocked by a bot check" instead. Hypothesis, not reproduced yet. Tier T2, open.

- **P1-25 Dedupe pages that are the same page.** Owner run on a 50-page retail site, 2026-11-10: the home page appeared under several paths (`/`, `/ref=nav_logo`, `/ref=footer_logo`) and the sign-in page appeared many times because protected links redirect to it. `normalize()` strips hash, query and trailing slash only. Fix: dedupe by `page.url()` after navigation, drop `/ref=...`-style tracking segments in `normalize()`, and skip a page whose screenshot hash matches one already captured; count skips in `report.json`. Fixture: add two aliases of the home page and two links that redirect to one login page. Tier T2.
- **P1-26 Never print a blank page.** Same run: some sheets were empty. A capture whose blank-row map is almost all blank (above 98 percent) is skipped with `blank page` in `report.json`, never flowed into the book. Fixture: add an empty page. Tier T1.
- **P1-27 Footer once on every site.** Same run: the footer repeated on most pages. `pageCss` hides `footer` on every page except the last, so a footer that is not a `footer` element stays; large sites use `div[role=contentinfo]` or id-based footers. Broaden the selector list and, when a block of identical rows ends every page, detect and drop it after the first page. Fixture: footer as `div#footer` on every page. Tier T2.
- **P1-23 Spill captures to disk and add a per-page pixel budget.** Reader feedback on the launch post, 2026-11-12: every page PNG stays in `shots[]` in `src/cli.mjs` until `buildBook` runs, so 50 tall pages hold 50 compressed PNGs at once (raw upper bound 1440 x 32 767 x 4 bytes x 50, about 8.8 GiB; the PNG footprint is smaller and unmeasured) before the PDF starts. `layout.mjs` needs only `height` and `blankRows`. Fix: `capture()` writes the PNG to a temp file and returns its path; `buildBook` and `buildSheets` read slices with `sharp(path)`; the temp dir is removed in the run-level `finally`. Same commit or the next: a per-page pixel budget (`width x height`) that skips the page with `exceeded page-pixel budget` in `report.json` instead of failing the run. Alternative under discussion: stream each page into the PDF as it is captured so nothing is stored, at the cost of reordering the retry pass so late pages keep their place. Neither is final; owner wants a third option. Memory on a 50-page run is a hypothesis, not measured; measure on the fixture first. Tier T2. Issue: https://github.com/piyushagru/site2paper/issues/1
- **P1-24 Per-page status in `report.json`.** Same feedback: today a reader cannot tell an intentional filmstrip from a page that never rendered. Add `status` per page: `ok`, `cut` (height cap), `filmstrip` (scroll story), `skipped` (budget), `failed` (with reason). `pages`, `failed` and `truncated` stay for one release, then collapse into the per-page list under P2-2 (`schemaVersion`). Tier T1. Issue: https://github.com/piyushagru/site2paper/issues/2
- **P1-8 Stitch pages taller than the cap.** With the cap now at 32 767 device px, pages past the cap lose their tail. Capture in viewport-sized clips and stitch with `sharp` so no row is lost; the hosted-tool guidance is "clip into sub-32767 pieces and stitch". Tier T2. Issue: https://github.com/piyushagru/site2paper/issues/4. Source: https://errors.standardbeagle.com/microsoft/playwright/cannot-take-screenshot-larger-than-32767-pixels-on-62dff6/, seen 2026-11-09.
- **P1-3 Add a CI guard for the Node engine floor.** Run `npm test` and the smoke on Node 20.9 as well as Node 24 so the floor stays true. Known today (2026-11-11): on Node 20 `node --test 'test/**/*.test.mjs'` runs zero tests, because the glob is only expanded from Node 21; `node --test test/` fixes it. Tier T1.

## P2

- **P2-11 New-user smoke on Linux without Chrome.** The Chromium download path and Linux have never run from the packed tarball as a new user; the local container runtime did not start on 2026-11-11. Add a CI job on ubuntu with no Chrome that runs `npm run smoke`. Tier T2.
- **P2-14 Gzipped sitemaps read as garbage.** `fetchText()` in `src/discover.mjs` returns `res.text()`; a `sitemap.xml.gz` or a nested `.gz` sitemap served as `application/gzip` (no `content-encoding` header, so `fetch` does not inflate it) yields no `<loc>` matches and the site silently falls back to the crawl. Smallest fix: read `arrayBuffer()`, and when the URL ends in `.gz` or the first two bytes are `1f 8b`, `gunzipSync` from `node:zlib` before decoding. Tier T1. Source: [sitemaps.org protocol](https://www.sitemaps.org/protocol.html) (gzip allowed, 50 MB uncompressed), deep dive 2026-11-12.
- **P2-15 `<loc>` wrapped in CDATA is skipped.** `parseSitemap()` matches `<loc>\s*([^<\s]+)`, so `<loc><![CDATA[https://...]]></loc>` (emitted by some generators) matches nothing: the sitemap is found, zero pages come out, and the crawl runs instead. Smallest fix: accept an optional `<![CDATA[` ... `]]>` wrapper in the regex and decode `&amp;` in the URL, with one parse test per shape. Hypothesis on how common CDATA is; the fix is five lines. Tier T1. Source: [sitemaps.org protocol](https://www.sitemaps.org/protocol.html) (entity escaping of `<loc>`), deep dive 2026-11-12.
- **P2-13 Unexpected errors carry the bug link.** `bin/site2paper.mjs` prints `site2paper: <message>` and exits 1 for every error that is not a usage error, with no way to tell a bug from a bad site. Append `Report it at <bugs.url from package.json>` to errors that are not usage (exit 2) or site (`no pages found`, `every page failed`) errors. Tier T1. Source: [clig.dev, Errors](https://clig.dev/#errors) ("make it effortless to submit bug reports"), deep dive 2026-11-11.
- **P2-1 One PDF per page.** Competitor parity with `website2pdf`, which writes one PDF per page with an optional merge. Add `--split` for one file per page. Tier T2. Source: https://github.com/jgazeau/website2pdf
- **P2-2 Make `report.json` self-describing.** Add a `schemaVersion` field so tools that read the report can detect changes. Tier T1.
- **P2-3 Document Chrome reuse.** Explain in the README when the tool uses an installed Chrome or Edge and when it downloads Chromium. Tier T1.
- **P2-5 WebP sheets as an option.** shot-scraper 1.12 added WebP output with a quality setting (2026-09). A `--image webp` flag for the per-page PNGs would cut output size; the PDF path is unchanged. Tier T2. Source: https://cybercorsairs.com/webp-screenshots-land-in-shot-scraper-1-12/, seen 2026-11-09.
- **P2-6 Mobile viewport preset.** Hosted tools ship desktop, tablet and mobile presets; site2paper has `--width` only. A `--device mobile` alias for width 390 with a mobile user agent covers the ask. Tier T2. Source: https://apify.com/webify-lab/website-screenshot-pdf/api/cli, seen 2026-11-09.
- **P2-7 Pages that scroll inside a container.** App shells with `html, body { height: 100% }` and `main { overflow: auto }` keep `window.scrollY` at 0, so `scrollWalk` never moves and `scrollHeight` reports one viewport. Detect the tallest scrollable element after `pagePrepScript`, make it `overflow: visible; height: auto` so the document grows to its content, then walk as today. Tier T2 (touches rules and capture, needs a fixture). Source: gap found reading `capture.mjs` on 2026-11-10 after the smooth-scroll fix.
- **P2-8 Lazy background images and `data-src` loaders.** CSS `background-image` set by lazysizes, lozad or `data-bg` attributes is outside `document.images`, so the final image wait cannot see it; a slow one leaves a grey block. Copy `data-src` and `data-srcset` to `src` and `srcset` on images that have no `src`, and give the walk one extra 300 ms settle when any `[data-bg]` or `.lazyload` element exists. Tier T2. Source: the curlshot post lists `background-image`, `<video>` posters and canvas as not covered by any wait, seen 2026-11-10.
- **P2-10 Freeze scroll-driven reveal state before the screenshot.** JS-driven stories set `opacity` and `transform` from the scroll position (the scroll-story example site, its product unit: `opacity: 0`, translated, three.js canvas inside). The walk reaches the revealed state, then `scrollTo(0, 0)` and the full-page screenshot put it back to the initial state, so the 3D product prints as empty backdrop. After the walk, at each pinned section's end, copy the computed `opacity` and `transform` of its descendants to inline `!important` styles, then scroll back. One state per element, no re-run of the story. Tier T2, `pagePrepScript` plus `scrollWalk`. Applies only to fixed frames whose parent is body (not detected as stories by P1-13); pinned sections are already printed as filmstrips. Source: probe of the scroll-story example site on 2026-11-10 (sticky and hidden element dump).
- **P2-4 Bulk list input.** Hosted tools take a pasted URL list and return one file per URL (Apify "Website Screenshot & PDF", seen 2026-11-09, https://apify.com/magenta_waterwheel/website-screenshot-pdf). A `--urls file.txt` flag that skips discovery covers the same ask. Tier T2.

## Needs decision

- **Redirect and private-network check before each navigation.** Same feedback, 2026-11-12: same-origin crawling is not a network safety boundary. A redirect or a DNS change can send a public URL to localhost or a cloud metadata address. Today nothing checks `page.url()` after `goto`, and no address range is blocked. Only matters for a hosted service or untrusted URL lists; the local CLI runs with the user's own network rights. If either lands: resolve the host before each request, refuse loopback, link-local and private ranges, and never log session cookies or bundle auth-walled captures into shared reports. Owner decision. Issue: https://github.com/piyushagru/site2paper/issues/3
- **Publish workflow.** Context seen 2026-11-09: trusted publishing now allows several trusted-publisher configs per package and holds staged versions until npm's malware scan completes (GitHub Changelog 2026-09-03, via https://www.refontelearning.com/blog/npm-multi-trusted-publishing-release-governance); the keyv@6.0.0 (2026-08-04) and @tanstack (2026-05-11) incidents show provenance attests the build, not the source, https://ecorpit.hashnode.dev/npm-provenance-signed-the-malware-on-4-august-2026-what-attestations-prove-and-what-a-cooldown-stops. Official docs: https://docs.npmjs.com/trusted-publishers. Added 2026-11-10: the GHAPPIER loader attack (2026-09-09) turned push access into publish access by editing a trusted-publishing release workflow, so the workflow file itself needs branch protection, https://orca.security/resources/research/ghappier-loader-npm-supply-chain-attack/. `docs/RELEASING.md` describes `.github/workflows/publish.yml` for trusted publishing, but the file does not exist. Adding it is a release-path change. Owner decision.
- **Text output for LLM and RAG use.** Competitor parity with `site2pdf`, which extracts page text. This is a new output format and a new output contract. Source: https://github.com/laiso/site2pdf. Owner decision.
- **Header and footer templates.** Competitor parity with `website2pdf`. This adds a new config surface, which conflicts with the zero-config rule in `AGENTS.md`. Source: https://github.com/jgazeau/website2pdf. Owner decision.
- **Scripted capture from a YAML list.** Competitor parity with `shot-scraper`. This adds a config file. Source: https://shot-scraper.datasette.io/. Owner decision.
